# Git Workflow Protocol

## Ветки
- `main` (или `master`) — защищена. Никогда не коммить и не пушить в неё напрямую.
- Для любой задачи, включая Fast-track, создавай рабочую ветку: `git checkout -b fix/<кратко>` или `feat/<кратко>`.
- Исключение: пользователь явно сказал «коммить в main» / «без PR» на эту сессию — тогда можно, но только для этой задачи, не по умолчанию впредь.

## Коммиты
- Один коммит = одно логическое изменение. Сообщение на русском, формат `тип: описание` (`feat`, `fix`, `refactor`, `chore`, `docs`).
- `git commit --amend` разрешён ТОЛЬКО если коммит ещё не запушен. Проверка: `git log @{u}..HEAD` (если ветка без upstream — коммит точно локальный). Если коммит уже есть на remote — амэнд запрещён, делай новый коммит поверх.

## Push и Pull Request
- После коммита НЕ пушь автоматически, если только:
  - пользователь явно попросил автопуш для этой сессии, ИЛИ
  - это черновая рабочая ветка агента, и пользователь заранее согласился на автопуш именно в неё (не в `main`).
- Стандартный путь:
  1. `git push -u origin <ветка>`
  2. Если `gh auth status` ок — `gh pr create --fill --base main`
  3. Сообщи пользователю ссылку на PR. НЕ мержи сам.
- Мерж в `main` — только с явного разрешения пользователя в моменте. «Чтобы не забыть» — не причина мержить самому.
- `git push --force` / `--force-with-lease` — запрещены без явного запроса пользователя в текущем сообщении.

## Секреты перед коммитом
- Проверь `git diff` на ключи, токены, пароли, `.env`-значения.
- Если в проекте есть pre-commit hook (`git-secrets`, `detect-secrets`, husky-хук) — не обходи его флагом `--no-verify`.
- Если хука нет — один раз предложи пользователю его настроить, дальше не повторяй предложение в каждой сессии.

## Работа с существующим remote (для Init существующего проекта)
- Проверь `git remote -v` до любых действий с удалённым репозиторием.
  - `origin` уже есть → используй его, `gh repo create` запрещён.
  - `origin` нет → спроси пользователя, создавать ли новый репозиторий, прежде чем действовать.
