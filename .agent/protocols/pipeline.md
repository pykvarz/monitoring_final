# Dynamic Pipeline (порядок работы)

Предполагается, что Detect Project State (`bootstrap.md`) уже выполнен. Оцени характер запроса и выбери путь: правки — Путь А или Б, только проверка без изменений — Путь В. Если сомневаешься между А и Б — выбирай Б.

## Путь А: Fast-track
Якоря: правка стилей, переименование, опечатки, мелкий рефакторинг.
1. Если для задачи ещё нет рабочей ветки — создай (см. `git-workflow.md`).
2. Пиши код, проверяй линтером.
3. **Sanity Check:** если для изменённого файла есть тесты — прогони их (smoke-test).
4. **Adversarial Check (быстрый):** просмотри `git diff` на случайные артефакты, опечатки, граничные случаи.
5. Коммит и push — строго по `git-workflow.md` (не в `main` напрямую, без автопуша без разрешения).

## Путь Б: Full Pipeline
Якоря: API-эндпоинт, БД/миграции, новая сущность, интеграция.
1. **Context Sync:** прочитай релевантный файл из `.agent/stack-rules/` и сверься с `memory-bank/`.
   Критическое правило: если для стека нет подробных правил — остановись и попроси их загрузить.
2. **Discovery** (`.agent/skills/grill-me.md`): задай вопросы по логике и краевым случаям.
   *Escape Hatch:* если пользователь отвечает «на твоё усмотрение» / «хватит» / «начинай» (или иначе явно передаёт решение тебе) — прекращай допрос и переходи к шагу 3.
3. **Architecture** (`.agent/skills/design-an-interface.md` + `design.md` раздел 1): спроектируй контракты/типы, покажи пользователю, значимые решения зафиксируй как ADR.
   Если задача включает новый/изменённый UI — дополнительно пройди `design.md` раздел 2, прежде чем писать код компонентов.
4. **TDD** (`.agent/skills/tdd.md`): напиши падающие тесты на проектируемые интерфейсы.
5. **Implementation:** напиши код для прохождения тестов.
6. **QA & Review:** полный цикл из `qa.md` (базовый QA + adversarial review).
7. **Memory Update:** зафиксируй прогресс и решения в `memory-bank/` (см. `memory-bank.md`).
8. **Version Control:** коммит, push в ветку, PR — строго по `git-workflow.md`. Мерж в `main` — только с явного разрешения пользователя.

## Путь В: Audit / Security Review
Якоря: «проверь на баги», «найди уязвимости», «аудит», «code review без изменений», «что не так с приложением».

1. **Read-only режим:** не создавай ветку, не пиши и не меняй код, не делай commit/push. Единственный вывод этого пути — отчёт.
2. Прочитай релевантные файлы проекта (весь проект или конкретный модуль, если пользователь указал область).
3. Проверь по категориям:
   - **Логические баги и граничные случаи:** null/undefined, пустые значения, гонки, повторные запросы.
   - **Уязвимости:** инъекции (SQL/NoSQL/командные), XSS/CSRF, небезопасная работа с секретами и токенами, отсутствие/неверная авторизация и валидация входных данных.
   - **Зависимости:** устаревшие или уязвимые пакеты (сверься с манифестом и известными CVE, если есть доступ).
   - **Нарушения стандартов проекта:** см. `standards.md`, `memory-bank/systemPatterns.md` и релевантный файл из `.agent/stack-rules/`, если он есть для этого стека.
4. Оформи находки в отчёт по каждому пункту: **Критичность** (Critical/High/Medium/Low) → **Описание** → **Где** (файл/строка) → **Как исправить** (кратко).
5. Не исправляй сам, если явно не попросили — только после отчёта спроси, что чинить в первую очередь.
6. `memory-bank/` не трогай по итогам аудита, если только не обнаружено расхождение с реальным кодом — тогда это Drift Detection (`memory-bank.md`), сообщи отдельно.

## Миграции БД (если применимо)
- Только через штатный инструмент проекта (см. `techContext.md`), никогда не руками в схеме.
- Миграция — отдельный коммит от бизнес-логики.
