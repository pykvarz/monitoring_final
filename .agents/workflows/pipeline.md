# Dynamic Pipeline (порядок работы)

Предполагается, что Detect Project State (`bootstrap.md`) уже выполнен. Оцени характер запроса и выбери путь: правки — Путь А или Б, только проверка без изменений — Путь В. Если сомневаешься между А и Б — выбирай Б.
Если это баг, воспроизведённый в реальном использовании — см. `qa.md` → Bug → Regression Test, до обычного TDD-цикла.

**Обязательная контрольная точка:** прежде чем написать хотя бы одну строку кода, явно сообщи пользователю одной строкой, какой путь выбран и почему («Выбираю Full Pipeline — это новая сущность/API»). Если выбран Путь Б — нельзя писать код, пока не пройден шаг Discovery (задать вопросы и получить ответы или явный Escape Hatch). Молчаливый переход сразу к коду без объявления пути — нарушение протокола, даже если результат в итоге окажется правильным.

## Путь А: Fast-track
Якоря: правка стилей, переименование, опечатки, изолированный рефакторинг без изменения контрактов.
**ВНИМАНИЕ (Scope Gate):** Добавление нового функционала, новых фич или изменение бизнес-логики в Пути А КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО (даже если кажется, что это «всего 3 строчки»). Если задача меняет поведение системы или добавляет возможность — немедленно эскалируй в Путь Б (Full Pipeline).

1. Пиши код прямо в `main`.
2. **QA & Targeted Behavioral Verification:**
   - Базовый QA по `qa.md` (обязательно линтер и проверка типов перед коммитом, smoke-тесты затронутых файлов).
   - **Targeted Behavioral Verification (обязательно):** реально запусти рантайм и выполни именно то действие / сценарий, который был затронут правкой (открыть страницу и проверить кликабельность/отображение изменённого элемента, вызвать отрефакторенную функцию с аргументами, проверить вывод изменённого текста). Пассивный запуск («сервер поднялся и слушает порт») НЕ считается проверкой — ты обязан подтвердить, что само изменение дало ожидаемый целевой эффект в рантайме.
3. **Adversarial Check (быстрый):** просмотри `git diff` на случайные артефакты, опечатки, граничные случаи и соблюдение Surgical Changes (`standards.md` — не задет ли лишний/соседний код). Завершается скиллом `verification-before-completion` (с фиксацией артефакта, доказывающего целевой эффект: скриншот, лог вызова).
4. Коммит и push — строго по `git-workflow.md`.

## Путь Б: Full Pipeline
Якоря: API-эндпоинт, БД/миграции, новая сущность, интеграция.
1. **Context Sync:** сверься с разделами System Patterns и Tech Context в `memory-bank/context.md`, прежде чем проектировать решение.
2. **Discovery** — скилл `brainstorming`: прогони идею через него, пока логика и краевые случаи не прояснятся, прежде чем фиксировать архитектуру.
   *Escape Hatch:* если пользователь отвечает «на твоё усмотрение» / «хватит» / «начинай» (или иначе явно передаёт решение тебе) — прекращай допрос и переходи к шагу 3.
3. **Architecture:** спроектируй контракты, типы и API-поверхность. Покажи пользователю до реализации, согласуй ключевые решения. Зафиксируй принятые паттерны и контракты в разделе System Patterns файла `memory-bank/context.md`.
4. **TDD** — скилл `test-driven-development`: падающий тест → минимальная реализация → повтор, один шов за цикл. Не пиши реализацию раньше падающего теста.
5. **Implementation:** доводи код до прохождения текущего цикла TDD, не забегая вперёд спекулятивным функционалом.
6. **QA & Verification Loop:** обязательный сквозной прогон цикла верификации по `qa.md`:
   - Unit / Integration тесты зелёные.
   - E2E сценарий пройден целиком (сквозной пользовательский путь через Playwright/инструмент или сквозной скриптовый сценарий).
   - Runtime verification пройдена (сервис/скрипт реально запущен в живом рантайме, проверены логи и консоль).
   - При любой ошибке/падении — автоматический переход в **Failure analysis** (`systematic-debugging`) → **Fix** → **Repeat** (снова упавший шаг + E2E + runtime). Запрещено объявлять задачу готовой или переходить к ревью с непройденными проверками.
   - Только после прохождения всех уровней — `verification-before-completion` с формированием артефакта-доказательства.
   - После успешной верификации — скилл `requesting-code-review` (сформулируй запрос на ревью по его формату, даже если ревьюер — ты сам в режиме адверсариал-чтения). Если получен ответ — обрабатывай через `receiving-code-review`.
7. **Memory Update:** зафиксируй прогресс и решения в `memory-bank/context.md` (см. `memory-bank.md`).
8. **Version Control:** коммит и push в `main` — по `git-workflow.md`.

Для задач, распадающихся на независимые куски (например, несколько эндпоинтов без общих зависимостей) — рассмотри `subagent-driven-development` или `dispatching-parallel-agents` вместо последовательного прохода шагов 4-6 по одному куску за раз.

## Путь В: Audit / Security Review
Якоря: «security review», «/security-review», «проверь на уязвимости», «найди баги безопасности», «аудит», «code review без изменений», «что не так с приложением».

Основной метод этого пути — скилл `systematic-debugging` (для общего анализа багов) и локальный скилл `.agents/skills/security-review/SKILL.md` (при аудите безопасности и уязвимостей). Веди его read-only: находи и объясняй, не чини по ходу.

1. **Read-only режим:** не создавай ветку, не пиши и не меняй код, не делай commit/push. Единственный вывод этого пути — отчёт.
2. Прочитай релевантные файлы проекта (весь проект или конкретный модуль, если пользователь указал область).
3. **Динамическая проверка (обязательна, не заменяется чтением кода):** поведенческие баги не видны при простом чтении кода — их видно только при реальном запуске.
   - Запусти линтер, проверку типов и весь существующий набор unit/integration тестов (команды из `memory-bank/context.md`, раздел Tech Context → «Команды»). Все упавшие тесты и ошибки типов зафиксируй в отчёт.
   - Подними локальное окружение/сервер, если это возможно в текущей среде.
   - Пройди по ключевым пользовательским сценариям: возьми их из раздела Project Brief в `memory-bank/context.md`, а если там нет — спроси у пользователя 2-3 типичных сценария реального использования.
   - Проверь граничные и нетипичные вводы (пустые поля, спецсимволы, повторные клики, отмена на середине действия, некорректные форматы, быстрые повторные действия).
   - Для уведомлений проверь переходы статусов: OFFLINE → ONLINE отправляет восстановление, WAITING → ONLINE — нет; отключённые уведомления не отправляются, обновление статуса и сброс простоя работают в каждом случае.
   - Для браузерных интеграций проверь фактический результат сохранения отдельно от закрытия формы: новая карточка (включая hash-маршруты) с видимыми полями, прежняя карточка, изменение только query, редирект на авторизацию и серверный отказ. Ложный отказ при успешно созданной заявке также считается дефектом.
   - Проверь консоль браузера / логи сервера на ошибки и warning, даже если внешне всё работает.
   - **E2E runtime проверка (обязательна):** прогони хотя бы один полный пользовательский путь от начала до конца через реальный рантайм (CLI/API + сервис + БД), а не по частям. Минимум — критический happy-path сценарий из раздела Project Brief в `memory-bank/context.md`. Если в проекте есть E2E-тесты — запусти их; если нет — пройди сценарий вызовами вручную и зафиксируй результат. Отдельно отметь: проходит ли путь целиком без падений, сохраняются ли данные между шагами, нет ли рассинхрона клиент/вызывающий код ↔ бэкенд ↔ БД. Пропуск E2E без явного обоснования (например, «нет рантайма в текущей среде») — неполный аудит.
4. Проверь по категориям:
   - **Логические баги и граничные случаи:** null/undefined, пустые значения, гонки, повторные запросы.
   - **Уязвимости:** инъекции (SQL/NoSQL/командные), XSS/CSRF, небезопасная работа с секретами и токенами, отсутствие/неверная авторизация и валидация входных данных.
   - **Зависимости:** устаревшие или уязвимые пакеты (сверься с манифестом и известными CVE, если есть доступ).
   - **Нарушения стандартов проекта:** см. `standards.md` и раздел System Patterns в `memory-bank/context.md`.
5. Оформи находки в отчёт по каждому пункту: **Критичность** (Critical/High/Medium/Low) → **Описание** → **Где** (файл/строка) → **Как исправить** (кратко).
6. Не исправляй сам, если явно не попросили — только после отчёта спроси, что чинить в первую очередь. Когда пользователь выберет пункты для исправления — переходи к ним через Путь А или Б, а не правь прямо внутри Audit.
7. `memory-bank/context.md` не трогай по итогам аудита, если только не обнаружено расхождение с реальным кодом — тогда это Drift Detection (`memory-bank.md`), сообщи отдельно.

## Миграции БД (если применимо)
- Только через штатный инструмент проекта (см. раздел Tech Context в `memory-bank/context.md`), никогда не руками в схеме.
- Миграция — отдельный коммит от бизнес-логики.
