# Dynamic Pipeline (порядок работы)

Предполагается, что Detect Project State (`bootstrap.md`) уже выполнен. Оцени характер запроса и выбери путь: правки — Путь А или Б, только проверка без изменений — Путь В. Если сомневаешься между А и Б — выбирай Б.
Если это баг, воспроизведённый в реальном использовании — см. `qa.md` → Bug → Regression Test, до обычного TDD-цикла.

**Обязательная контрольная точка:** прежде чем написать хотя бы одну строку кода, явно сообщи пользователю одной строкой, какой путь выбран и почему («Выбираю Full Pipeline — это новая сущность/API»). Если выбран Путь Б — нельзя писать код, пока не пройден шаг Discovery (задать вопросы и получить ответы или явный Escape Hatch). Молчаливый переход сразу к коду без объявления пути — нарушение протокола, даже если результат в итоге окажется правильным.

## Путь А: Fast-track
Якоря: правка стилей, переименование, опечатки, мелкий рефакторинг.
1. Пиши код прямо в `main`.
2. **QA & Sanity Check:** базовый QA по `qa.md` (обязательно линтер и проверка типов перед коммитом), плюс прогони тесты, если они есть для изменённых файлов (smoke-test).
3. **Adversarial Check (быстрый):** просмотри `git diff` на случайные артефакты, опечатки, граничные случаи и соблюдение Surgical Changes (`standards.md` — не задет ли лишний/соседний код). Завершается скиллом `verification-before-completion` (для мелких правок это может быть просто «прогнал реальный сценарий»).
4. Коммит и push — строго по `git-workflow.md`.

## Путь Б: Full Pipeline
Якоря: API-эндпоинт, БД/миграции, новая сущность, интеграция.
1. **Context Sync:** сверься с разделами System Patterns и Tech Context в `memory-bank/context.md`, прежде чем проектировать решение.
2. **Discovery** — скилл `brainstorming`: прогони идею через него, пока логика и краевые случаи не прояснятся, прежде чем фиксировать архитектуру.
   *Escape Hatch:* если пользователь отвечает «на твоё усмотрение» / «хватит» / «начинай» (или иначе явно передаёт решение тебе) — прекращай допрос и переходи к шагу 3.
3. **Architecture:** спроектируй контракты/типы (см. `design.md`, раздел 1), покажи пользователю, значимые решения зафиксируй как ADR.
   Если задача включает новый/изменённый UI — дополнительно пройди `design.md` раздел 2, прежде чем писать код компонентов.
4. **TDD** — скилл `test-driven-development`: падающий тест → минимальная реализация → повтор, один шов за цикл. Не пиши реализацию раньше падающего теста.
5. **Implementation:** доводи код до прохождения текущего цикла TDD, не забегая вперёд спекулятивным функционалом.
6. **QA & Review:** базовый QA из `qa.md`, затем перед ревью — `verification-before-completion`. После этого скилл `requesting-code-review` — сформулируй запрос на ревью по его формату, даже если ревьюер — ты сам в режиме адверсариал-чтения. Если пользователь или другой агент прислал ревью — обрабатывай его через `receiving-code-review`.
7. **Memory Update:** зафиксируй прогресс и решения в `memory-bank/context.md` (см. `memory-bank.md`).
8. **Version Control:** коммит и push в `main` — по `git-workflow.md`.

Для задач, распадающихся на независимые куски (например, несколько эндпоинтов без общих зависимостей) — рассмотри `subagent-driven-development` или `dispatching-parallel-agents` вместо последовательного прохода шагов 4-6 по одному куску за раз.

## Путь В: Audit / Security Review
Якоря: «проверь на баги», «найди уязвимости», «аудит», «code review без изменений», «что не так с приложением».

Основной метод этого пути — скилл `systematic-debugging`, применённый не к одному известному багу, а ко всей затронутой области кода. Веди его read-only: находи и объясняй, не чини по ходу.

1. **Read-only режим:** не создавай ветку, не пиши и не меняй код, не делай commit/push. Единственный вывод этого пути — отчёт.
2. Прочитай релевантные файлы проекта (весь проект или конкретный модуль, если пользователь указал область).
3. **Динамическая проверка (обязательна, не заменяется чтением кода):** поведенческие баги не видны при простом чтении кода — их видно только при реальном запуске.
   - Подними локальное окружение/сервер, если это возможно в текущей среде.
   - Пройди по ключевым пользовательским сценариям: возьми их из раздела Project Brief в `memory-bank/context.md`, а если там нет — спроси у пользователя 2-3 типичных сценария реального использования.
   - Проверь граничные и нетипичные вводы (пустые поля, спецсимволы, повторные клики, отмена на середине действия, некорректные форматы, быстрые повторные действия).
   - Проверь консоль браузера / логи сервера на ошибки и warning, даже если внешне всё работает.
   - **E2E runtime проверка (обязательна):** прогони хотя бы один полный пользовательский путь от начала до конца через реальный рантайм (UI + API + БД), а не по частям. Минимум — критический happy-path сценарий из раздела Project Brief в `memory-bank/context.md` (регистрация → логин → основное действие → logout, или эквивалент для проекта). Если в проекте есть E2E-тесты (Playwright/Cypress/etc.) — запусти их; если нет — пройди сценарий вручную и зафиксируй результат. Отдельно отметь: проходит ли путь целиком без падений, сохраняются ли данные между шагами, нет ли рассинхрона UI ↔ бэкенд ↔ БД. Пропуск E2E без явного обоснования (например, «нет рантайма в текущей среде») — неполный аудит.
4. Проверь по категориям:
   - **Логические баги и граничные случаи:** null/undefined, пустые значения, гонки, повторные запросы.
   - **Уязвимости:** инъекции (SQL/NoSQL/командные), XSS/CSRF, небезопасная работа с секретами и токенами, отсутствие/неверная авторизация и валидация входных данных.
   - **Зависимости:** устаревшие или уязвимые пакеты (сверься с манифестом и известными CVE, если есть доступ).
   - **Нарушения стандартов проекта:** см. `standards.md` и раздел System Patterns в `memory-bank/context.md`.
5. Оформи находки в отчёт по каждому пункту: **Критичность** (Critical/High/Medium/Low) → **Описание** → **Где** (файл/строка) → **Как исправить** (кратко).
6. Не исправляй сам, если явно не попросили — только после отчёта спроси, что чинить в первую очередь. Когда пользователь выберет пункты для исправления — переходи к ним через Путь А или Б, а не правь прямо внутри Audit.
7. `memory-bank/context.md` не трогай по итогам аудита, если только не обнаружено расхождение с реальным кодом — тогда это Drift Detection (`memory-bank.md`), сообщи отдельно.

## Миграции БД (если применимо)
- Только через штатный инструмент проекта (см. раздел Tech Context в `memory-bank/context.md`), никогда не руками в схеме.
- Миграция — отдельный коммит от бизнес-логики.
