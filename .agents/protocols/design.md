# Design Protocol

Два разных типа «дизайна» — не путай их:
- **Архитектурный дизайн** — контракты, типы, структура кода. Раздел 1.
- **UI/UX дизайн** — визуал, компоненты, стиль интерфейса. Раздел 2.

---

## 1. Архитектурный дизайн (шаг Architecture в Full Pipeline)

1. Перед написанием кода спроектируй контракты/типы/API-поверхность. Покажи пользователю **до** реализации, не после. Для стресс-теста черновой архитектуры уместен скилл `brainstorming` — прогони спорные решения через него, прежде чем фиксировать ADR.
2. Если решение значимое (новая сущность, смена паттерна, выбор между 2+ подходами) — зафиксируй его как ADR (Architecture Decision Record):
   - Файл: `.agents/adr/000N-краткое-название.md` (нумерация по порядку).
   - Формат: **Контекст** (что решаем и почему) → **Решение** (что выбрали) → **Альтернативы** (что рассматривали и почему отклонили) → **Последствия** (что это меняет, какие компромиссы).
3. Мелкие, локальные решения (Fast-track) в ADR не выносим — им место в `memory-bank/systemPatterns.md`, если паттерн повторяемый.
4. ADR не переписываются задним числом. Если решение отменено — создай новый ADR со ссылкой на отменённый, не редактируй старый.

## 2. UI/UX дизайн

Якоря: новый экран/страница, новый компонент, редизайн существующего UI, лендинг, дашборд.

### Если пользователь не дизайнер (по умолчанию для этого проекта)
Не спрашивай про цвета, шрифты, hex-коды, layout-концепции — пользователь не обязан в этом разбираться. Вместо этого:
1. Агент сам выбирает современный, аккуратный вид по умолчанию, ориентируясь на актуальные тренды в вебе/UI для этого типа продукта (если не уверен, что сейчас актуально — можно свериться поиском в интернете перед первым UI-артефактом проекта).
2. Показывай выбор в простых человеческих формулировках, а не в технических: «сделаю светлую тему, спокойные синие акценты, современный минимализм» — а не «#1A56DB, Inter 500».
3. Дай пользователю выбрать из 2-3 простых направлений, если это уместно (например: «минимализм», «яркий и дружелюбный», «строгий корпоративный»), через понятные слова, а не термины.
4. После выбора — дальше следуй обычному процессу ниже, но не проси пользователя утверждать технические детали токенов. Технические детали фиксируются в `designSystem.md` автоматически, пользователю показывается только результат (сам экран).

### Правило персистентности (главное отличие от разового дизайна)
Дизайн одной сессии не должен противоречить дизайну другой. Перед тем как проектировать что-либо визуальное:
1. Проверь, существует ли `memory-bank/designSystem.md`.
   - **Есть** → используй его палитру, типографику, токены отступов и компоненты как есть. Не изобретай новые токены без причины — расширяй, а не заменяй.
   - **Нет** → это первый UI-артефакт проекта. После проектирования — создай `designSystem.md` и зафиксируй в нём выбранные токены, чтобы следующая сессия не начинала с нуля.

### Процесс (для нового экрана/раздела)
1. **Определи предмет:** для кого это, какая у экрана главная задача, что пользователь должен понять или сделать за первые секунды. Если бриф это не называет — предложи сам и подтверди с пользователем.
2. **Спроектируй токен-систему** (или сверься с существующей из `designSystem.md`):
   - Цвет: 4–6 именованных hex-значений.
   - Типографика: 1–2 семейства шрифтов и их роли.
   - Layout: концепция в одно предложение + ASCII-каркас, включая выравнивание.
   - Принципы: что делает именно этот экран узнаваемым, а не шаблонным.
3. **Сверь план с брифом** до кода: если результат похож на то, что ты сделал бы для любого похожего запроса — это шаблонный дефолт, переделай и объясни, что изменил.
4. **Реализуй.** Держи специфичность CSS-селекторов аккуратной (частая проблема — конфликтующие по силе селекторы для отступов между секциями).
5. **Проверь качественный минимум:** адаптивность до мобильного, видимый focus для клавиатуры, уважение `prefers-reduced-motion`, доступные цветовые контрасты.
6. **Самокритика:** если окружение позволяет — сделай скриншот и сверь с планом. Спроси себя: это решение конкретно для этого проекта, или дефолт, который я бы предложил в любом похожем брифе?
7. Обнови `designSystem.md` новыми или изменёнными токенами/компонентами.

### Частые «шаблонные» тэллы, которых стоит избегать по умолчанию
(если бриф явно не просит именно это — тогда бриф важнее)
- Кремовый фон + serif-заголовок + терракотовый акцент.
- Почти чёрный фон + один яркий неоновый акцент.
- Одинаковые скруглённые карточки с одной и той же серой тенью на всё подряд.
- ALL-CAPS лейблы, разделители из точек (·), стрелки (→) в конце каждой кнопки/ссылки.
- Акцентирование одного слова в заголовке курсивом/цветом без причины.

## 3. Фронтенд не должен расходиться с бэкендом

Частая причина поломок — не дизайн, а рассинхрон данных: бэкенд возвращает одни поля/типы, фронтенд ожидает другие.

Правило: контракт (список полей, типов, эндпоинтов), спроектированный на шаге Architecture (раздел 1), — единственный источник правды.
- Храни его в одном месте, доступном обеим сторонам: например `shared/types.ts`, OpenAPI/Swagger-схема, или файл в `memory-bank/systemPatterns.md`.
- Если меняется бэкенд-контракт (новое поле, переименование, другой тип) — сначала обнови общий файл контракта, потом бэкенд, потом фронтенд. Никогда не подстраивай фронтенд под то, что бэкенд «на самом деле» возвращает в обход контракта — это и есть источник рассинхрона.
- Перед тем как считать задачу с UI и API вместе завершённой (Definition of Done в `qa.md`) — сверь, что фронтенд использует актуальную версию контракта, а не устаревшую копию типов.

### designSystem.md — минимальная структура
```
## Токены
- Цвета: ...
- Типографика: ...
- Отступы/сетка: ...

## Компоненты
- Кнопка (варианты, состояния)
- Карточка
- Форма
...

## Принципы
- (1-2 предложения про общий стиль/тон проекта)
```
