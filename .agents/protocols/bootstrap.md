# Bootstrap Protocol

## Универсальная команда входа: `ag-start`
Когда пользователь пишет `ag-start` отдельным сообщением — выполни:

1. **Detect Project State:** проверь, существует ли `memory-bank/`, есть ли в проекте код.
2. **Check Superpowers:** проверь, что скиллы superpowers доступны (например, есть ли реакция на `skill(using-superpowers)` или запись о плагине). Если недоступны — сообщи об этом явно и предложи установить: `agy plugin install https://github.com/obra/superpowers`. Без него шаги, ссылающиеся на `test-driven-development`, `brainstorming`, `systematic-debugging` и т.д. в `pipeline.md`, не будут работать как задумано — не подменяй их импровизацией молча.
3. **Route by state:**
   - Пустой проект + нет `memory-bank/` → Init (холодный старт, пустой проект).
   - Есть код + нет `memory-bank/` → Init (холодный старт, существующий проект).
   - Есть `memory-bank/` → прочитай все файлы (`memory-bank.md`), выполни Drift Detection, **дополнительно проверь**, существует ли `.agents/stack-rules/` и не пуста ли она (см. п. 2 выше про superpowers отдельно). Если отсутствует или пуста — сообщи об этом явно и предложи выполнить Stack-rules Setup сейчас (см. Init ниже), прежде чем продолжать. Затем кратко (3-5 строк) резюмируй состояние проекта («Вот что я помню: …») и спроси, что делаем дальше.
4. После Detect Project State — жди описание задачи, затем выбирай Fast-track или Full Pipeline (`.agents/workflows/pipeline.md`).

## Init — пустой проект (нет memory-bank, нет кода)
1. Создай базовую структуру `memory-bank/`.
2. Задай вопросы о сути проекта (для кого, что делает, ключевые сценарии), чтобы заполнить `projectbrief.md`. Для этого шага уместен скилл `brainstorming`, если у пользователя пока только смутная идея, а не готовый список требований.
3. **Выбор стека:** на основе ответов предложи 2-3 варианта стека технологий в простых словах, без узкоспециальных терминов там, где можно обойтись:
   - для каждого варианта — 1-2 предложения плюсов и минусов применительно к именно этому проекту (не общие абстрактные плюсы фреймворка).
   - дождись, пока пользователь выберет один из вариантов (или явно попросит другой стек, не из предложенных).
   - зафиксируй выбор в `memory-bank/techContext.md`, включая раздел «Команды» (см. `memory-bank.md`) — как только определятся реальные команды проекта (после первого `npm init`/аналога).
4. **Stack-rules Setup (только теперь, когда стек известен):** клонируй `https://github.com/PatrickJS/awesome-cursorrules.git` во временную папку, выбери ТОЛЬКО 1-3 файла под выбранный стек, переименуй понятно (`web.md`, `backend.md`) и скопируй в `.agents/stack-rules/`. Категорически не копируй весь каталог правил. Удали временную папку. Если репозиторий недоступен — сгенерируй эталонное содержимое сам.
5. **Git & GitHub Setup** (детали — `git-workflow.md`), теперь, когда `memory-bank/` реально заполнена:
   - `git init`, `git branch -M main`, `git add .`, `git commit -m "feat: начальная структура проекта и memory-bank"`.
   - Проверь `gh auth status`. Если ок — спроси: «Создать удалённый репозиторий на GitHub и запушить код?». При «да»: `gh repo create <имя-папки> --private --source=. --remote=origin --push`.
6. Не пиши код приложения, пока не закрыты пункты 2-4.

## Init — существующий проект (нет memory-bank, но есть код)
1. **Быстрое определение стека:** просмотри манифесты (package.json/requirements.txt/go.mod/Cargo.toml и т.п.), чтобы понять стек проекта — этого достаточно для следующего шага, полный анализ будет позже.
2. **Stack-rules Setup:** создай `.agents/stack-rules/`, если её нет. Клонируй `https://github.com/PatrickJS/awesome-cursorrules.git`, выбери ТОЛЬКО 1-3 файла под определённый стек, скопируй в `.agents/stack-rules/`. Категорически не копируй весь каталог. Удали временную папку. Если репозиторий недоступен — сгенерируй эталонное содержимое сам.
3. **Git & Remote Check** (детали — `git-workflow.md`):
   - Нет `.git` → `git init`, `git branch -M main`, `git add .`, `git commit -m "feat: исходное состояние существующего проекта"`.
   - Проверь `git remote -v`:
     - `origin` уже есть → используй его, новый репозиторий не создавай.
     - `origin` нет → проверь `gh auth status`, спроси: «Создать удалённый репозиторий на GitHub и привязать к проекту?». При согласии: `gh repo create <имя-папки> --private --source=. --remote=origin --push`.
4. Проанализируй структуру проекта подробно (манифесты зависимостей, файлы, паттерны, реальный стек). Заполни `techContext.md` (включая раздел «Команды», см. `memory-bank.md`) и `systemPatterns.md`. Для первичного глубокого прохода по незнакомому коду уместен скилл `systematic-debugging`, даже если явных багов ещё не искали — он даёт структуру исследования, а не только починки.
5. Покажи черновик найденных паттернов для подтверждения. Задай уточняющие вопросы по неясному из кода (для `projectbrief.md`), прежде чем писать новый код.
