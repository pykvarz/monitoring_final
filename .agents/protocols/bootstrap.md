# Bootstrap Protocol

## Универсальная команда входа: `ag-start`
Когда пользователь пишет `ag-start` отдельным сообщением — выполни:

1. **Detect Project State:** проверь, существует ли `memory-bank/context.md`, есть ли в проекте код.
2. **Check Superpowers:** проверь, что скиллы superpowers доступны (например, есть ли реакция на `skill(using-superpowers)` или запись о плагине). Если недоступны — сообщи об этом явно и предложи установить: `agy plugin install https://github.com/obra/superpowers`. Без него шаги, ссылающиеся на `test-driven-development`, `brainstorming`, `systematic-debugging` и т.д. в `pipeline.md`, не будут работать как задумано — не подменяй их импровизацией молча.
3. **Route by state:**
   - Пустой проект + нет `memory-bank/context.md` → Init (холодный старт, пустой проект).
   - Есть код + нет `memory-bank/context.md` → Init (холодный старт, существующий проект).
   - Есть `memory-bank/context.md` → прочитай его целиком (см. `memory-bank.md`), выполни Drift Detection. Затем кратко (3-5 строк) резюмируй состояние проекта («Вот что я помню: …») и спроси, что делаем дальше.
4. После Detect Project State — жди описание задачи, затем выбирай Fast-track или Full Pipeline (`.agents/workflows/pipeline.md`).

## Init — пустой проект (нет memory-bank/context.md, нет кода)
1. Создай файл `memory-bank/context.md` со структурой разделов из `memory-bank.md`.
2. Задай вопросы о сути проекта (для кого, что делает, ключевые сценарии), чтобы заполнить раздел Project Brief. Для этого шага уместен скилл `brainstorming`, если у пользователя пока только смутная идея, а не готовый список требований.
3. **Выбор стека:** сначала определи, точно ли нужен диалог (см. ниже), и только потом действуй.
   - **Предложи 2-3 варианта и жди выбора пользователя**, если верно оба условия: (а) это не разовый скрипт/утилита, а проект с долгим циклом жизни (кто-то будет его поддерживать, деплоить, нанимать под него людей), и (б) реально есть 2+ разумных варианта без явного победителя для этой ситуации.
     - Для каждого варианта — 1-2 предложения плюсов и минусов применительно к именно этому проекту (не общие абстрактные плюсы фреймворка), простыми словами, без узкоспециальных терминов там, где можно обойтись.
     - Дождись, пока пользователь выберет один из вариантов (или явно попросит другой стек, не из предложенных).
   - **Выбери сам и явно назови выбор одной строкой** (без диалога), если верно любое из: это разовый скрипт/автоматизация; пользователь уже дал сильные сигналы, сужающие выбор до одного варианта («у меня уже есть Node-бэкенд», «хостинг только Python», «я знаю только JS») — предлагать в этом случае 2-3 варианта было бы показухой, а не реальным выбором.
   - В обоих случаях: зафиксируй выбор в разделе Tech Context файла `memory-bank/context.md`, включая подраздел «Команды» (см. `memory-bank.md`) — как только определятся реальные команды проекта (после первого `npm init`/аналога).
4. **Git & GitHub Setup** (детали — `git-workflow.md`), теперь, когда `memory-bank/context.md` реально заполнен:
   - `git init`, `git branch -M main`, `git add .`, `git commit -m "feat: начальная структура проекта и memory-bank"`.
   - Проверь `gh auth status`. Если ок — спроси: «Создать удалённый репозиторий на GitHub и запушить код?». При «да»: `gh repo create <имя-папки> --private --source=. --remote=origin --push`.
5. Не пиши код приложения, пока не закрыты пункты 2-3.

## Init — существующий проект (нет memory-bank/context.md, но есть код)
1. **Быстрое определение стека:** просмотри манифесты (package.json/requirements.txt/go.mod/Cargo.toml и т.п.), чтобы понять стек проекта — этого достаточно для следующего шага, полный анализ будет позже.
2. **Git & Remote Check** (детали — `git-workflow.md`):
   - Нет `.git` → `git init`, `git branch -M main`, `git add .`, `git commit -m "feat: исходное состояние существующего проекта"`.
   - Проверь `git remote -v`:
     - `origin` уже есть → используй его, новый репозиторий не создавай.
     - `origin` нет → проверь `gh auth status`, спроси: «Создать удалённый репозиторий на GitHub и привязать к проекту?». При согласии: `gh repo create <имя-папки> --private --source=. --remote=origin --push`.
3. Проанализируй структуру проекта подробно (манифесты зависимостей, файлы, паттерны, реальный стек). В `memory-bank/context.md` заполни разделы Tech Context (включая подраздел «Команды», см. `memory-bank.md`) и System Patterns. Для первичного глубокого прохода по незнакомому коду уместен скилл `systematic-debugging`, даже если явных багов ещё не искали — он даёт структуру исследования, а не только починки.
4. Покажи черновик найденных паттернов для подтверждения. Задай уточняющие вопросы по неясному из кода (для раздела Project Brief), прежде чем писать новый код.
