# Git Workflow Protocol

Это жёсткие правила именно этого проекта — ограничения, а не процедура. Проект работает напрямую в `main`, без веток и PR: скиллы `using-git-worktrees` и `finishing-a-development-branch` для этого проекта не применяются (они остаются доступны на случай, если пользователь явно попросит параллельную ветку под конкретную задачу).

## Ветки
- По умолчанию работай прямо в `main` (или `master`) — отдельную ветку не создавай.
- Исключение: пользователь явно попросил отдельную ветку под конкретную задачу — тогда веди её через `using-git-worktrees` / `finishing-a-development-branch`, но это разовое исключение, не смена дефолта.

## Коммиты
- Один коммит = одно логическое изменение. Сообщение на русском, формат `тип: описание` (`feat`, `fix`, `refactor`, `chore`, `docs`).
- `git commit --amend` разрешён ТОЛЬКО если коммит ещё не запушен. Проверка: `git log "@{u}..HEAD"` (кавычки обязательны для PowerShell; если ветка без upstream — коммит точно локальный). Если коммит уже есть на remote — амэнд запрещён, делай новый коммит поверх.

## Push
- После коммита в `main` пушь как обычный следующий шаг задачи (Fast-track и Full Pipeline включают Version Control как штатный шаг) — отдельного разрешения на сам факт пуша в `main` не требуется.
- `git push --force` / `--force-with-lease` — запрещены без явного запроса пользователя в текущем сообщении.

## Секреты перед коммитом
- Проверь `git diff` на ключи, токены, пароли, `.env`-значения.
- Если в проекте есть pre-commit hook (`git-secrets`, `detect-secrets`, husky-хук) — не обходи его флагом `--no-verify`.
- Если хука нет — один раз предложи пользователю его настроить, дальше не повторяй предложение в каждой сессии.

## Работа с существующим remote (для Init существующего проекта)
- Проверь `git remote -v` до любых действий с удалённым репозиторием.
  - `origin` уже есть → используй его, `gh repo create` запрещён.
  - `origin` нет → спроси пользователя, создавать ли новый репозиторий, прежде чем действовать.
