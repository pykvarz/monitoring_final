# Memory Bank Protocol (память проекта)

Вся память проекта — один файл `memory-bank/context.md` с разделами ниже (раньше это были отдельные файлы `projectbrief.md`/`systemPatterns.md`/`techContext.md`/`progress.md`/`designSystem.md` — теперь всё в одном месте, чтобы не терять связи между ними и не плодить дубли).

## Структура файла
```
# Memory Bank

## Project Brief
(для кого проект, что делает, ключевые сценарии)

## System Patterns
(архитектурные паттерны, устоявшиеся решения)

## Tech Context
(стек, конфигурация)

### Команды
- Установка зависимостей: ...
- Dev-сервер: ...
- Линтер: ...
- Проверка типов: ...
- Тесты: ...
- Сборка: ...

## Progress
(текущий статус: что сделано, что в работе)
```

## Read (всегда)
В начале новой сессии, если `memory-bank/context.md` уже существует — прочитай его целиком перед ответом на запрос.

## Write (при изменениях)
Обновляй нужный раздел при новых архитектурных решениях или закрытии фич. Правь точечно — не переписывай файл целиком ради одной правки.

## Context Prune (очистка от мусора)
Файл должен оставаться компактным:
- Фича закрыта → сотри подробности из раздела Progress (историю храним в Git, не в памяти агента).
- Паттерн устарел → удали из раздела System Patterns.
- Перед удалением архитектурного паттерна, который может ещё пригодиться, кратко упомяни это пользователю — не удаляй молча то, в чём не уверен.

## Drift Detection (расхождение памяти с реальностью)
Если при Read обнаружено расхождение между `memory-bank/context.md` и реальным состоянием кода (ручные правки, новые файлы, изменившийся стек) — сообщи об этом явно, прежде чем продолжать работу. Не доверяй файлу памяти слепо.

## Раздел «Команды» — обязателен
Подраздел «Команды» внутри Tech Context должен содержать точные команды для: установки зависимостей, запуска dev-сервера, линтера, проверки типов, тестов, сборки.
Если раздела нет — заполни его при первой возможности вместо того, чтобы каждый раз заново искать команды по `package.json`/манифестам.
