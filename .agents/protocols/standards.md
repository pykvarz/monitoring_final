# Universal Code Standards

Это базовые принципы по умолчанию. Если в разделах System Patterns или Tech Context файла `memory-bank/context.md` для проекта прописано конкретное решение (конкретная либа валидации, конкретный стиль обработки ошибок и т.п.) — оно имеет приоритет над общими пунктами ниже.

- **Fail Fast & Early Returns:** без вложенных `if/else`, `return` при первой же ошибке.
- **Strict Types & Validation:** внешние данные валидируются на границах системы (см. конкретный инструмент в разделе Tech Context файла `memory-bank/context.md`, например Zod/Pydantic). Тип `any`/`unknown`-без-проверки запрещён.
- **Search First (не изобретай заново):** перед созданием новой функции-утилиты, хелпера или валидатора всегда проверь кодовую базу поиском. Используй уже имеющиеся в проекте решения вместо пложения дублей.
- **Immutability by Default:** избегай мутации входных аргументов и структур данных in-place. Функции должны возвращать новые объекты/копии, исключая скрытые побочные эффекты.
- **File Size Ceiling:** ориентир — 200–400 строк на файл, 800 строк — абсолютный предел. Много небольших модулей с единой ответственностью лучше монолитных «божественных» файлов. При превышении лимита декомпозируй модуль.
- **Error Handling:** запрещено «проглатывать» ошибки молча.
- **DRY:** дубликаты кода и магические числа запрещены.
- **Naming & Readability:** имя переменной/функции понятно без чтения тела.
- **Security Baseline:** секреты — только через `.env`, с примером в `.env.example`. Никогда не хардкодить.
- **Observability:** значимые ошибки логируются структурированно, уровень логирования выбирается осознанно.

## Dependency & Stack Evolution
Запрещено добавлять новую библиотеку/технологию без явного согласования с пользователем. Сначала предложи решение существующими средствами.

Если согласовано внедрение принципиально новой мажорной технологии (новая БД, ORM, UI-фреймворк) — обнови раздел Tech Context в `memory-bank/context.md` и, если для новой технологии есть значимые специфические практики, зафиксируй их прямо в разделе System Patterns того же файла.

## Surgical Changes (при правке существующего кода)
- Трогай только то, что нужно для задачи — не «улучшай» по пути соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано, даже если сам сделал бы иначе.
- Соблюдай существующий стиль файла, даже если он не совпадает с твоими предпочтениями.
- Если твои правки сделали что-то неиспользуемым (импорт, переменную, функцию) — убери именно это.
- Заметил не связанный с задачей мёртвый код — упомяни пользователю, но не удаляй молча, если явно не попросили.
- Проверка: каждая изменённая строка должна прослеживаться к конкретному запросу пользователя.
