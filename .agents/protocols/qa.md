# QA & Review Protocol

## Базовый QA (всегда перед коммитом)
1. Запусти линтер, проверку типов и тесты — точные команды бери из `memory-bank/context.md`, раздел Tech Context → «Команды».
2. Если раздела «Команды» там нет — спроси пользователя и запиши его, прежде чем полагаться на угаданные команды.
3. Все проверки обязаны быть зелёными перед коммитом.

## Цикл верификации и исправления (Verification & Fix Loop)
Никакая задача не считается выполненной без сквозного подтверждения её работоспособности. Процесс строго цикличен:

1. **Implement:** реализация функционала (в рамках TDD — под падающие тесты, см. `.agents/workflows/pipeline.md`).
2. **Unit / Integration tests:** проверка отдельных модулей, функций и связок компонентов. Точные команды — из `memory-bank/context.md`, раздел Tech Context → «Команды».
3. **E2E scenario:** проверка реального пользовательского сценария целиком от начала до конца (end-to-end flow). Если в проекте есть E2E-фреймворк (Playwright, Cypress) — запуск тестов; если это CLI/скрипт/API без выделенного E2E-раннера — обязателен запуск сквозного сценария через реальные вызовы/скрипт с фиксацией вывода.
4. **Runtime verification:** реальный запуск приложения/скрипта в живом окружении (не только под тестовым раннером). Проверка: сервис успешно стартует, слушает порт, процесс завершается с корректным кодом, чистая консоль и логи сервера без unhandled exceptions и фатальных ошибок.
5. **Failure analysis:** если любая проверка на шагах 2–4 упала или выявила ошибку/варнинг — немедленно переключись на скилл `systematic-debugging`. Запрещено патчить наугад; сначала найди коренную причину (root cause).
6. **Fix:** устранение первопричины бага.
7. **Repeat:** после исправления обязателен повторный запуск проверок — начиная с упавшего уровня, и обязательный повторный сквозной прогон **E2E + Runtime verification**. Если проверка снова выявила ошибку — задача автоматически возвращается на этап исправления (с ограничением по Loop Breaker ниже).
8. **Final verification:** только после успешного прохождения ВСЕХ уровней проверок вызывается скилл `verification-before-completion` для формирования доказательства готовности.

## Code Review (перед коммитом)
Не изобретай свой чек-лист ревью — используй скилл `requesting-code-review`, чтобы оформить запрос по его формату (даже если ревьюер — ты сам, читающий свой же `git diff` вторым проходом). Если ревью прислали в ответ (пользователь, другой агент, CI) — обрабатывай его через `receiving-code-review`, а не читай комментарии как обычный текст.

Специфичные для этого проекта пункты, которые стоит держать в фокусе при ревью (дополняют, а не заменяют скилл):
- **Соответствие стандартам:** см. `standards.md` и раздел System Patterns в `memory-bank/context.md`.
- **Гигиена:** debug-логи (`console.log`/`print`), неиспользуемые импорты, закомментированный код, временные костыли.

Важно: саморевью тем же агентом, который писал код, имеет слепые зоны. Оно дополняет, но не заменяет реальные тесты, и не заменяет ревью человеком для Full Pipeline задач.

## Loop Breaker (защита от потери данных)
- Не более 3 попыток самостоятельно исправить одну и ту же ошибку в цикле Verification & Fix. Если проблема — поведенческий баг, а не опечатка, переключись на скилл `systematic-debugging` вместо повторных наугад попыток.
- Если не получилось: `git restore <только файлы, изменённые тобой в этой сессии>` — никогда `git restore .` (можно удалить ручную работу пользователя).
- Опиши план декомпозиции задачи и жди решения пользователя.

## Дополнительные проверки
- **Targeted Behavioral Verification** (обязательно для Fast-track): запрещено ограничиваться пассивным запуском («сервер стартовал без ошибок»). Обязателен реальный триггер изменённого участка в рантайме (вызов отрефакторенной функции, проверка ответа эндпоинта, сверка вывода) с подтверждением получения ожидаемого эффекта и чистой консолью/логами.
- **Service & Scripts QA:** проверка корректности кодов возврата процесса (exit code 0), тестовый прогон с реальными или mock-данными, проверка логов на warnings/errors.

## Bug → Regression Test (закрываем пробел в проверках навсегда)
Если пользователь сообщает о баге, найденном при реальном использовании (то есть Audit его пропустил):
1. Найди и воспроизведи баг через скилл `systematic-debugging` — не чини вслепую по описанию.
2. Через скилл `test-driven-development` напиши тест, который бы поймал именно этот баг, ДО исправления (тест должен упасть на текущем коде).
3. Исправь код, чтобы тест прошёл.
4. Если баг — представитель целого класса похожих ситуаций (не разовая случайность) — добавь его как категорию в шаг 3 «Динамическая проверка» в `.agents/workflows/pipeline.md` (Путь В), чтобы будущий Audit тоже проверял такие сценарии, а не только этот конкретный случай.

Так каждый пропущенный вручную найденный баг делает будущие автоматические проверки чуть умнее, а не остаётся разовой заплаткой.

## Verification (доказательство, что работает)
Перед тем как объявить задачу выполненной — прогони `verification-before-completion`. Агент не имеет права сказать «готово» без реального доказательства работы. Нельзя заявлять «готово», если функционал не был реально запущен и проверен в рантайме (для Fast-track — подтверждён целевой эффект правки через Targeted Behavioral Verification). Если E2E/runtime-проверка выявила ошибку — задача автоматически возвращается на этап исправления (Failure analysis → Fix → Repeat).
Минимум доказательства для этого проекта — воспроизводимый артефакт (лог успешного прогона тестов и рантайма, запись вывода сценария/ответа сервиса), а не «я посмотрел на код и вроде ок».

## Definition of Done
- [ ] Линтер и проверка типов зелёные
- [ ] Unit / Integration тесты зелёные
- [ ] E2E сценарий пройден целиком (для Full Pipeline)
- [ ] Runtime verification пройдена (для Full Pipeline — сервис/скрипт запущен, логи чистые; для Fast-track — подтверждён целевой эффект через Targeted Behavioral Verification)
- [ ] Verification пройдена (`verification-before-completion`), есть артефакт-доказательство
- [ ] Code Review пройден (`requesting-code-review` / `receiving-code-review`)
- [ ] `.env.example` обновлён, если появились новые переменные
- [ ] README обновлён, если изменился интерфейс/команды
- [ ] `memory-bank/context.md` обновлён (включая System Patterns при смене архитектуры)
- [ ] Изменения закоммичены и запушены в `main`
