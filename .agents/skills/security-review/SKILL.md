# Security Review Protocol & Checklist

Этот скилл обеспечивает глубокий аудит безопасности кодовой базы. 
Он выявляет потенциальные уязвимости, утечки данных и архитектурные огрехи.

## Режим выполнения
- **Strictly Read-Only:** аудит проводится в режиме чтения (в рамках Пути В пайплайна).
- **Запрещено** автоматически менять код до презентации отчёта пользователю.
- Результатом аудита является структурированный отчёт с конкретными безопасными примерами исправления.

---

## Чек-лист проверок (Security Review Checklist)

### 1. Secrets & Credentials (Утечки секретов)
- [ ] **Хардкод секретов:** отсутствие API-ключей, токенов, паролей, приватных ключей в исходном коде.
- [ ] **Конфигурация окружения:** все секреты загружаются строго через переменные окружения (`.env`).
- [ ] **Изоляция:** файл `.env` надёжно исключён в `.gitignore`, в репозитории присутствует только актуальный `.env.example` без реальных значений.
- [ ] **История Git:** отсутствие случайно закоммиченных секретов в истории коммитов.

### 2. Input Validation & Sanitization (Валидация на границах)
- [ ] **Валидация на входе:** все внешние данные (тело запроса, query-параметры, заголовки, аргументы CLI) валидируются строгими схемами (Zod, Pydantic, validator) на внешних границах системы. Типы `any` / `unknown` без проверки запрещены.
- [ ] **Path Traversal:** отсутствие конкатенации путей с пользовательским вводом без санитизации и проверки выхода за пределы рабочей директории (`../`).
- [ ] **Загрузка файлов (если есть):**
  - Ограничение максимального размера файла.
  - Строгий whitelist разрешённых MIME-типов и расширений (не доверять заголовку `Content-Type` от клиента слепо).
  - Генерация случайного безопасного имени файла на сервере.

### 3. Injection Prevention (Защита от инъекций)
- [ ] **SQL / NoSQL Injection:** любые запросы к базам данных выполняются строго через параметризацию или ORM/Query Builder. Категорически запрещена конкатенация строк или f-строки при формировании запросов.
- [ ] **Command Injection:** отсутствие передачи непроверенного пользовательского ввода в системные оболочки (`exec`, `spawn`, `subprocess`, `os.system`, `eval`, `child_process`).
- [ ] **XSS / HTML Injection (для сервисов с выводом):** корректное экранирование данных, отдаваемых клиенту, безопасные заголовки.

### 4. Authentication & Authorization (AuthN & AuthZ)
- [ ] **BOLA / IDOR (Broken Object Level Authorization):** на каждом эндпоинте с идентификатором (`/api/items/:id`) проверяется принадлежность объекта текущему авторизованному пользователю/организации, а не просто факт наличия токена.
- [ ] **Хранение токенов/сессий:** токены авторизации не должны храниться в открытом `localStorage` (уязвимо к XSS). Рекомендуются `HttpOnly`, `Secure`, `SameSite` cookies.
- [ ] **Принцип наименьших привилегий:** проверка ролей (RBAC) до выполнения бизнес-логики.
- [ ] **Brute Force Protection:** наличие rate limiting или защиты от перебора на чувствительных точках входа (логин, сброс пароля, отправка кодов).

### 5. Data Exposure & Observability (Утечки данных)
- [ ] **Логирование:** логи не содержат паролей, токенов, номеров карт и персональных данных (PII).
- [ ] **Обработка ошибок:** клиенту не отдаются внутренние стектрейсы, дампы БД или архитектурные подробности при возникновении 500 ошибок.

### 6. Dependencies & Supply Chain (Зависимости)
- [ ] **CVE в пакетах:** запуск штатного аудитора зависимостей (`npm audit`, `pip-audit`, `cargo audit` и т.д.).
- [ ] **Неиспользуемые/подозрительные зависимости:** отсутствие лишних или устаревших пакетов.

## Формат отчёта (Security Review Report)

По итогам проверки сформируй отчёт в формате:

```markdown
# Security Review Report

## Резюме
Краткое описание общего состояния безопасности проекта и количества найденных проблем.

## Найденные уязвимости

### [CRITICAL / HIGH / MEDIUM / LOW]: <Краткое название>
- **Где:** `путь/к/файлу.ts:строка`
- **Угроза:** подробное объяснение вектора атаки и последствий.
- **Уязвимый код:**
\`\`\`ts
// проблемный фрагмент
\`\`\`
- **Рекомендация по исправлению:**
\`\`\`ts
// безопасный вариант исправления
\`\`\`

---

## Следующие шаги
Спроси у пользователя, какие пункты взять в работу в первую очередь (для исправления через Путь Б с TDD).
```
